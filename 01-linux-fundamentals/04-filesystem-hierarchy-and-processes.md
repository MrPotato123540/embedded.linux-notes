# Filesystem Hierarchy, Processes and Permissions

> **Applies to:** PetaLinux 2024.1 · Zynq UltraScale+ MPSoC · any Linux system

**[01 · Linux Fundamentals](README.md)** · Part I: Foundations

## In short

- Linux has a single directory tree that starts at `/`. The **Filesystem Hierarchy Standard (FHS)** says what goes where. Embedded distributions follow it, with a few twists such as volatile `/var/log`.
- Several directories are not on any disk: `/proc`, `/sys`, `/dev` and `/run` are **virtual filesystems** generated by the kernel. They are how you inspect and control the running system and its hardware.
- Every process runs as a user. Access is decided by file **permissions** (owner, group, others), a few special bits (setuid, sticky) and, for root, **capabilities**.
- Hardware is reached through **device nodes** in `/dev`. Each one is identified by a type (character or block) and a **major:minor** number pair.

## Concepts

### The directory tree

The root directory of the reference target:

```console
target$ ls /
bin         configfs    etc         lib         media       proc        sbin        sys         usr
boot        dev         home        lost+found  mnt         run         srv         tmp         var
```

| Directory | Contents | On the reference target |
| --- | --- | --- |
| `/bin`, `/sbin` | Essential commands; `sbin` for system administration | Mostly symlinks to `/bin/busybox`; `/sbin/init` → `../lib/systemd/systemd` |
| `/lib` | Shared libraries, kernel modules (`/lib/modules/<kernel version>`), firmware (`/lib/firmware`) | Firmware for the VCU (`al5d.fw`, `al5e.fw`) and the RPU demos (`image_echo_test`, ...) |
| `/usr` | Everything else that is read-only: most programs, libraries, data | `/usr/bin`, `/usr/lib`, `/usr/share` |
| `/etc` | System configuration, as text files | `/etc/passwd`, `/etc/ssh/`, `/etc/systemd/`, `/etc/yum.repos.d/` |
| `/var` | Variable data: logs, caches, spool, package databases | `/var/log` and `/var/tmp` point to the RAM-backed `/var/volatile` |
| `/tmp` | Temporary files, cleared at boot | A `tmpfs` in RAM |
| `/run` | Runtime state since boot: PID files, sockets | A `tmpfs` in RAM |
| `/home` | Home directories of normal users | `/home/petalinux` |
| `/boot` | Kernel and bootloader files, when the root filesystem holds them | Empty; the kernel is loaded by U-Boot from the boot medium |
| `/media`, `/mnt` | Mount points for removable and temporary filesystems | |
| `/opt` | Add-on application packages | Not present; create it if your application uses it |
| `/proc`, `/sys`, `/dev` | Virtual filesystems (next section) | |
| `/configfs` | A second mount point of the kernel's configfs | Specific to this image; configfs is also mounted at `/sys/kernel/config` |
| `/lost+found` | Recovered fragments after an ext4 check | Present because the root filesystem is ext4 |

> [!NOTE]
> Modern desktop distributions **merge** `/bin`, `/sbin` and `/lib` into `/usr`. On the Ubuntu host, `/bin` is a symlink:
>
> ```console
> $ ls -ld /bin /lib
> lrwxrwxrwx 1 root root 7 May 13 10:54 /bin -> usr/bin
> lrwxrwxrwx 1 root root 7 May 13 10:54 /lib -> usr/lib
> ```
>
> On the PetaLinux 2024.1 target, `/bin` is a real directory. Scripts that hard-code `/usr/bin/foo` versus `/bin/foo` can behave differently on the two systems.

The `/var` layout is worth a closer look, because it surprises people who keep logs on the target:

```console
target$ ls -l /var | head -12
total 20
drwxr-xr-x    2 root     root          4096 Mar  9  2018 backups
drwxr-xr-x    8 root     root          4096 Oct 15 11:46 cache
drwxr-xr-x   13 root     root          4096 Oct 15 11:46 lib
drwxr-xr-x    2 root     root          4096 Mar  9  2018 local
lrwxrwxrwx    1 root     root            11 Mar  9  2018 lock -> ../run/lock
lrwxrwxrwx    1 root     root            12 Mar  9  2018 log -> volatile/log
lrwxrwxrwx    1 root     root             6 Mar  9  2018 run -> ../run
drwxr-xr-x    3 root     root          4096 Mar  9  2018 spool
lrwxrwxrwx    1 root     root            12 Mar  9  2018 tmp -> volatile/tmp
drwxrwxrwt    4 root     root            80 Oct 15 12:13 volatile
```

`/var/volatile` is a `tmpfs`, so everything written to `/var/log` and `/var/tmp` is lost at every reboot. Yocto does this on purpose: it protects flash memory from constant log writes and makes a read-only root filesystem possible. [Chapter 15](../15-root-filesystem-and-init/01-rootfs-fundamentals.md) shows how to change it when you need persistent logs.

### Virtual filesystems

`mount` shows what is mounted where. Trimmed to the interesting lines:

```console
target$ mount
proc on /proc type proc (rw,relatime)
sysfs on /sys type sysfs (rw,relatime)
devtmpfs on /dev type devtmpfs (rw,relatime,size=1496452k,nr_inodes=374113,mode=755)
/dev/mmcblk0 on / type ext4 (rw,relatime)
devpts on /dev/pts type devpts (rw,relatime,gid=5,mode=620,ptmxmode=666)
tmpfs on /run type tmpfs (rw,nosuid,nodev,size=805012k,nr_inodes=819200,mode=755)
cgroup2 on /sys/fs/cgroup/unified type cgroup2 (rw,nosuid,nodev,noexec,relatime,nsdelegate)
...
debugfs on /sys/kernel/debug type debugfs (rw,nosuid,nodev,noexec,relatime)
tmpfs on /tmp type tmpfs (rw,nosuid,nodev,size=2012532k,nr_inodes=1048576)
configfs on /sys/kernel/config type configfs (rw,nosuid,nodev,noexec,relatime)
tmpfs on /var/volatile type tmpfs (rw,relatime)
...
```

Only `/dev/mmcblk0` is a real storage device (the SD card, ext4). Everything else is generated by the kernel or lives in RAM:

| Filesystem | Mounted at | What it is for |
| --- | --- | --- |
| `proc` | `/proc` | Processes (`/proc/<pid>/`) and kernel state (`/proc/cpuinfo`, `/proc/meminfo`, `/proc/interrupts`, `/proc/cmdline`) |
| `sysfs` | `/sys` | The kernel's device model: devices, drivers, buses, classes; many attributes are writable |
| `devtmpfs` | `/dev` | Device nodes, created by the kernel as drivers register devices |
| `devpts` | `/dev/pts` | Pseudo-terminals for SSH sessions and terminal emulators |
| `tmpfs` | `/run`, `/tmp`, `/var/volatile`, `/dev/shm` | Files in RAM |
| `cgroup2` (and v1 `cgroup`) | `/sys/fs/cgroup` | Control groups, used by systemd to track and limit services |
| `debugfs` | `/sys/kernel/debug` | Kernel debugging interfaces (root only) |
| `configfs` | `/sys/kernel/config` | Objects created from user space: USB gadgets, device tree overlays |

Reading the hardware through them:

```console
target$ cat /proc/cpuinfo | head -9
processor	: 0
BogoMIPS	: 130.00
Features	: fp asimd aes pmull sha1 sha2 crc32 cpuid
CPU implementer	: 0x41
CPU architecture: 8
CPU variant	: 0x0
CPU part	: 0xd03
CPU revision	: 4
target$ cat /proc/device-tree/model; echo
ZynqMP ZCU106 RevA
target$ grep -c processor /proc/cpuinfo; head -3 /proc/meminfo
4
MemTotal:        4025060 kB
MemFree:         3784052 kB
MemAvailable:    3762552 kB
```

Implementer `0x41` is Arm and part `0xd03` is the Cortex-A53. `Features` lists the Armv8 crypto extensions (`aes`, `sha1`, `sha2`, `pmull`) that OpenSSL uses for fast TLS. `/proc/device-tree` is the device tree the kernel booted with ([chapter 12](../12-device-tree/06-device-tree-debugging.md)). The memory size reflects QEMU's `-m 4G`; a real ZCU106 reports its own DDR size.

`/sys/class` groups devices by function. On a ZynqMP system several classes map directly to SoC features covered later in this guide:

```console
target$ ls /sys/class | tr '\n' ' '
aie ata_device ata_link ata_port backlight bdi block bluetooth bsg char devcoredump devlink dma dma_heap drm dvb extcon fpga_bridge fpga_manager fpga_region gpio graphics hwmon i2c-adapter i2c-dev ieee80211 input iommu leds mdio_bus mem misc mmc_host mtd net pci_bus phy power_supply pps ptp pwm regulator remoteproc rfkill rtc scsi_device scsi_disk scsi_host sound spi_master tpm tpmrm tty ubi udc uio usb_role usbmisc vc vfio vfio-dev video4linux vtconsole wakeup watchdog xlnxsync
```

`fpga_manager` and `fpga_region` ([chapter 17](../17-pl-integration-and-dfx/03-fpga-manager.md)), `remoteproc` ([chapter 21](../21-rpu-and-openamp/03-remoteproc-and-rpmsg.md)), `uio` ([chapter 14](../14-kernel-modules-and-drivers/05-user-space-hardware-access.md)), `video4linux` ([chapter 20](../20-video-and-multimedia/01-v4l2-fundamentals.md)) and `drm` ([chapter 19](../19-graphics-and-display/01-display-subsystem-and-drm-kms.md)) all have their own chapters.

### Users, groups and permissions

```console
target$ id
uid=1000(petalinux) gid=1000(petalinux) groups=19(input),29(audio),44(video),987(aie),1000(petalinux)
target$ ls -l /etc/passwd /etc/shadow /usr/bin/sudo
-rw-r--r--    1 root     root          1236 Mar  9  2018 /etc/passwd
-r--------    1 root     root           838 Oct 15 11:55 /etc/shadow
---s--x--x    1 root     root        269200 Mar  9  2018 /usr/bin/sudo
target$ ls -ld /tmp /home/petalinux
drwxr-xr-x    3 petalinu petalinu      4096 Oct 15 12:10 /home/petalinux
drwxrwxrwt   11 root     root           320 Oct 15 12:14 /tmp
target$ umask
0022
```

Reading the permission string `-rw-r--r--`:

| Position | Meaning |
| --- | --- |
| 1 | Type: `-` file, `d` directory, `l` symlink, `c` character device, `b` block device |
| 2-4 | Owner permissions: `r` read, `w` write, `x` execute (for a directory: may enter it) |
| 5-7 | Group permissions |
| 8-10 | Permissions of everyone else |

Three special cases appear above:

- **`/etc/shadow`** holds the password hashes, so only root may read it (`-r--------`). `/etc/passwd` holds user names, IDs, home directories and shells, and is world-readable.
- **setuid (`s` in the owner's execute position).** `sudo` runs as its *owner*, root, whoever starts it. That is how a normal user can become root after authenticating. setuid-root programs are an obvious attack target; on this image the list includes `/bin/busybox` itself, which is worth remembering for [chapter 27](../27-linux-and-network-security/01-linux-hardening.md):

  ```console
  target$ find / -xdev -perm -4000 -type f 2>/dev/null
  /sbin/mount.nfs
  /bin/busybox
  /bin/umount.util-linux
  /bin/mount.util-linux
  /bin/su.shadow
  ...
  /usr/bin/sudo
  ...
  ```

- **sticky bit (`t` in the last position).** In `/tmp` (`drwxrwxrwt`) everyone may create files, but only a file's owner may delete it.

`umask 0022` removes write permission for group and others from newly created files, so new files are `rw-r--r--` and new directories `rwxr-xr-x`.

**Root and sudo.** PetaLinux 2024.1 has no root password login by default. The `petalinux` user is allowed to run any command through sudo:

```console
target# grep -v '^#' /etc/sudoers | grep -v '^$'
root ALL=(ALL:ALL) ALL
@includedir /etc/sudoers.d
target# cat /etc/sudoers.d/*
petalinux ALL=(ALL) ALL
```

**Capabilities.** The kernel does not really check "is this root?". It checks individual privileges called capabilities (`CAP_NET_ADMIN`, `CAP_SYS_RAWIO`, ...). Root normally has all of them, a normal user none:

```console
target$ grep -E '^(Name|Uid|CapEff)' /proc/self/status
Name:	grep
Uid:	1000	1000	1000	1000
CapEff:	0000000000000000
target# grep -E '^(Name|Uid|CapEff)' /proc/self/status
Name:	grep
Uid:	0	0	0	0
CapEff:	000001ffffffffff
```

Giving a service only the capabilities it needs, instead of running it as root, is a key hardening technique ([chapter 27](../27-linux-and-network-security/01-linux-hardening.md)).

### Processes

A process is a running program with its own address space, PID, user, open files and parent. New processes are created with `fork()` and start another program with `exec()`. The first user-space process, **PID 1**, is started by the kernel and is the ancestor of all others:

```console
target# ls -l /proc/1/exe
lrwxrwxrwx    1 root     root             0 Oct 15 12:13 /proc/1/exe -> /lib/systemd/systemd
target$ ps -ef | head -8
PID   USER     TIME  COMMAND
    1 root      0:08 {systemd} /sbin/init
    2 root      0:00 [kthreadd]
    3 root      0:00 [pool_workqueue_]
    4 root      0:00 [kworker/R-rcu_g]
    5 root      0:00 [kworker/R-rcu_p]
    6 root      0:00 [kworker/R-slub_]
    7 root      0:00 [kworker/R-netns]
```

Names in brackets are **kernel threads**, children of `kthreadd` (PID 2). They do kernel work (deferred I/O, RCU, interrupt handling) and never run user code. `ps` here is the BusyBox applet, which accepts `-ef` but prints fewer columns than the procps version on your host.

**Signals** are how processes are told to stop, reload or terminate:

```console
target$ sleep 300 & echo "started PID $!"
[1] 927
started PID 927
target$ ps -o pid,ppid,stat,user,comm | grep -E 'PID|sleep'
PID   PPID  STAT USER     COMMAND
  927   883 S    petalinu sleep
target$ kill -TERM %1; wait %1; echo "exit status of sleep: $?"
[1]+  Terminated              sleep 300
exit status of sleep: 143
```

`S` means sleeping, waiting for an event. A process killed by a signal exits with status 128 + signal number, so `143` is `SIGTERM` (15). The most important signals:

| Signal | Number | Default action | Typical use |
| --- | --- | --- | --- |
| `SIGHUP` | 1 | Terminate | Terminal closed; many daemons reload their configuration instead |
| `SIGINT` | 2 | Terminate | Ctrl-C |
| `SIGKILL` | 9 | Terminate, cannot be caught | Last resort; the program cannot clean up |
| `SIGSEGV` | 11 | Terminate and dump core | Invalid memory access |
| `SIGTERM` | 15 | Terminate | Polite request to exit; systemd sends it when stopping a service |
| `SIGSTOP`, `SIGCONT` | 19, 18 | Stop, continue | Pausing a process (Ctrl-Z sends `SIGTSTP`) |

A **daemon** is a background process without a terminal, such as `sshd` or `systemd-timesyncd`. On a systemd system, daemons are started and supervised as services ([chapter 15](../15-root-filesystem-and-init/06-init-systems.md)).

### Everything is a file: device nodes

Drivers expose hardware as files in `/dev`. `ls -l` shows the type (`c` character, `b` block) and the **major, minor** number pair instead of a size:

```console
target$ ls -l /dev/ttyPS0 /dev/null /dev/mem
crw-r-----    1 root     kmem        1,   1 Oct 15 11:55 /dev/mem
crw-rw-rw-    1 root     root        1,   3 Oct 15 11:55 /dev/null
crw-------    1 petalinu tty       238,   0 Oct 15 11:56 /dev/ttyPS0
target$ ls -l /dev/i2c-0 /dev/gpiochip1 /dev/mmcblk0
crw-------    1 root     root      254,   1 Oct 15 12:13 /dev/gpiochip1
crw-------    1 root     root       89,   0 Oct 15 12:13 /dev/i2c-0
brw-rw----    1 root     disk      179,   0 Oct 15 12:13 /dev/mmcblk0
```

The **major** number selects the driver, the **minor** number the instance. `/proc/devices` lists the registered majors, and sysfs shows the numbers for each device:

```console
target$ head -12 /proc/devices
Character devices:
  1 mem
  2 pty
  3 ttyp
  4 /dev/vc/0
  4 tty
  4 ttyS
  5 /dev/tty
  5 /dev/console
  5 /dev/ptmx
  7 vcs
 10 misc
target$ cat /sys/class/tty/ttyPS0/dev
238:0
```

- **Character devices** are byte streams: serial ports, I2C buses, GPIO chips, `/dev/mem`.
- **Block devices** are addressed in blocks and can hold a filesystem: SD/eMMC (`mmcblk*`), SATA (`sd*`), MTD block devices (`mtdblock*`).
- `ttyPS0` is owned by `petalinux` because that user is logged in on the serial console; `login` hands the terminal to the user.
- `/dev/i2c-0` and `/dev/gpiochip1` are root-only (`crw-------`) on this image. A normal user needs `sudo`, or a udev rule that gives a group access ([chapter 15](../15-root-filesystem-and-init/08-device-management-and-udev.md)).

## On ZynqMP

Device names in `/dev` are not always what you expect. The ZynqMP has two PS UARTs, `ff000000` (UART0) and `ff010000` (UART1). On the reference image, UART1 does **not** become `ttyPS1`:

```console
target# dmesg | grep -i -E 'ttyPS|mmcblk0' | head -6
[    0.000000] Kernel command line: earlycon console=ttyPS0,115200 root=/dev/ram0 rw init_fatal_sh=1 cma=1000M
[    2.043106] ff000000.serial: ttyPS0 at MMIO 0xff000000 (irq = 22, base_baud = 2169921) is a xuartps
[    2.045213] printk: console [ttyPS0] enabled
[    2.051368] ff010000.serial: ttyPS2 at MMIO 0xff010000 (irq = 23, base_baud = 2169921) is a xuartps
[    3.085720] mmcblk0: mmc0:4567 QEMU! 2.00 GiB
[    6.465644] EXT4-fs (mmcblk0): mounted filesystem 3b837610-55ee-494c-a360-3ca957829a7a r/w with ordered data mode. Quota mode: none.
```

The `ttyPS` index comes from the `serialN` aliases in the device tree, and in this BSP `serial1` points to the debug communication channel (`/dcc`) rather than UART1. [Section 06](06-serial-console.md) shows the aliases.

## Pitfalls

- **Expecting files in `/tmp`, `/var/log` or `/var/tmp` to survive a reboot.** On PetaLinux they are in RAM.
- **Running everything as root to avoid permission errors.** Fix the permissions (groups, udev rules, capabilities) instead. Root-only device nodes are a reminder, not an obstacle.
- **Using `kill -9` first.** `SIGKILL` gives a program no chance to flush files or release hardware. Send `SIGTERM` and wait.
- **Hard-coding `/dev/ttyPS1` or `/dev/mmcblk1`.** Names depend on device tree aliases and probe order. Use the aliases you control, or the stable names under `/dev/disk/by-*` and `/dev/serial/by-*`.
