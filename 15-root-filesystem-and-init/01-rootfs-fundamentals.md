# Root Filesystem Fundamentals

> **Applies to:** PetaLinux 2024.1 · Zynq UltraScale+ MPSoC

**[15 · Root Filesystem and Init](README.md)** · Part VII: Root Filesystem and User Space

## What the root filesystem supplies

The root filesystem supplies the files userspace needs after kernel initialization: init, applications, configuration, libraries and the dynamic loader. A dynamically linked executable can exist and still fail with “not found” when its requested loader is missing.

`/dev` exposes device nodes. `/proc` and `/sys` expose kernel information and control interfaces through virtual filesystems. They are not ordinary static directories whose saved contents reproduce a running system.

## Image assembly

Yocto's `do_rootfs` installs selected packages and applies image policy. The manifest records package selection. Manual changes made after boot are outside that build record unless converted into recipes or configuration.

A read-only root simplifies recovery and prevents accidental system-file changes. Applications still need explicit writable locations for state, logs and temporary files. An overlay can provide writable behavior, but persistent overlay data needs migration and capacity management.

## Validation

Check init, the loader, required libraries, mounts and permissions. Test startup with an empty writable-data partition as well as an upgraded one.

## A pathname crosses several layers

The root filesystem gives the process its initial directory tree. The Virtual Filesystem (VFS) layer resolves pathnames and presents a common interface to different filesystem implementations. Mounts attach other filesystems to points in that tree. `/proc`, `/sys`, `/dev` and temporary files can therefore come from different sources than the storage containing `/usr`.

Opening `/etc/device.conf` first resolves the root and directory entries in the process's mount namespace. A symbolic link can redirect lookup. A mount can replace the visible directory below a path. This explains why inspecting the files inside a rootfs archive does not always show what a running service sees: startup may mount persistent configuration or an overlay over those paths.

A filesystem image and an archive also encode different things. An ext4 image contains filesystem structures for a block device. A tar or cpio archive contains entries that must be extracted into a filesystem. Renaming an archive to `.ext4` does not add a superblock or allocation metadata.

## Follow `/sbin/init` in the supplied rootfs

A read-only inspection of `pre-built/linux/images/rootfs.tar.gz` found `/sbin/init` as a symlink to `../lib/systemd/systemd`. The target file is an AArch64 ELF64 executable. Its program headers request `/lib/ld-linux-aarch64.so.1`, and its dynamic entries include `libsystemd-core-251.so`, `libsystemd-shared-251.so` and `libc.so.6`.

That chain matters. The kernel does not simply read the first bytes of `/sbin/init` and start a function. It resolves the symlink, checks executable permissions and format, maps the ELF segments, and loads the requested interpreter for a dynamic executable. The interpreter then resolves shared libraries before the program can run normally.

A present executable can therefore fail with an apparent missing-file error when its ELF interpreter is absent. A missing shared library fails at a different stage, after the interpreter starts. Neither problem is fixed by changing the executable's permissions to allow everyone to write it.

The archive's package manifest reports systemd `251.8` and glibc `2.36`. These are observed BSP artifacts, not promises about every image generated by PetaLinux 2024.1.

## Permissions are stored data

File ownership, mode bits, symlink targets, extended attributes and capabilities form part of the rootfs contract. Copying files through a filesystem or archive tool that loses those attributes can produce an image with the right filenames and wrong behavior.

For example, a device node needs its type and major/minor numbers, while a symlink needs its target rather than a copied target file. Executable mode affects program startup. File capabilities and set-user-ID behavior affect privilege. Review how the image build records these attributes; a directory listing that only shows names is insufficient.

Yocto uses controlled build-time ownership handling so recipes can create a target filesystem without installing everything as host root. The image task then assembles package contents and applies image policy. Hand-editing an extracted tree can be useful for investigation, but it is not a reproducible replacement for the recipe that should create the file.

## Read-only root does not mean no writable state

A product can keep its software image read-only while providing separate writable locations for logs, identity, application data and runtime sockets. Each location needs a lifetime: temporary until reboot, persistent across upgrades, or replaced with the software version.

Place runtime state such as sockets and process identifiers on a suitable temporary filesystem. Place durable application records on a managed persistent volume. Decide whether a factory reset erases each class. If configuration changes are stored in a writable overlay without a migration policy, an old upper-layer file can silently hide a new version in the updated base image.

Write failures should be interpreted against this policy. A read-only error may mean the design is working as intended, the wrong mount was selected, or the filesystem was remounted read-only after an error. These cases require different remedies.

## Size has several meanings

Compressed archive size is not rootfs RAM use. Extracted file size is not exact disk usage. An ext4 image has metadata and free-space policy, and sparse files can have a large logical size with fewer allocated blocks. An initramfs additionally needs memory for extraction, file data and kernel structures.

Use the quantity that matches the problem. Storage capacity planning needs deployed image and persistent-data growth. Boot memory planning needs the archive's placement and the extracted early userspace footprint. Application memory planning needs page cache, anonymous allocations and shared-library mappings during operation.

> [!NOTE]
> **Not run on the reference setup:** alternate rootfs boot and power-loss recovery. The archive and ELF inspection establish file layout and ABI inputs, not successful startup of a modified image.
